## 2. 判定词（只允许这四类，逐行写一个）

| 判定 | 写什么证据 | 不满足即不得使用 |
|---|---|---|
| `✅已对齐` | 新系统承接位置的类 + 方法（`src/main/java/...`，带行号）+ 覆盖它的自动化测试名 | 只有「页面能打开」或「接口能返回」不算 |
| `旧版无功能` | 旧版 PHP 文件与行号，说明为何没有可迁行为 | 必须有源码行；凭证删号一类不算 |
| `排除-<OP-n 或 D 编号>` | 该 OP/D 的编号与出处（决策记录位置） | 自己判断「不需要」不算，必须有已登记的 OP/D |
| `缺口` | 主文件 §9.1 对应的 `GAP-` 编号 | 没有 GAP- 行就写缺口 → 视为违规 |

**没有第五种写法。** 不允许留「未判定」、不允许「暂不判定」、不允许只写「见 B2x」。

## 3. 证据等级（扫描器给的候选，只是线索，不是判定）

扫描器把 376 行逐行打成候选承接位置，并标注证据强度：

| 等级 | 含义 | 人工要做的 |
|---|---|---|
| E1 | 新版有与旧方法同名的处理器方法 | 打开两处源码，确认语义与参数一致 |
| E2 | 新版有同名包/控制器类整体承接（如 `index/vod/*` → `site/web/Site*Controller`） | 逐个方法确认，**整类承接不等于逐行已对齐** |
| E3 | 后台动作由实现批次登记承接（`AdminPermissions.batchOf`） | 核对批次号是否就是已合并的批次，未合并的批次仍算缺口 |
| E4 | 新版登记「不提供」或「旧版无此方法」 | 核对文案与 `WITHOUT_LEGACY_METHOD` 是否与旧版一致 |
| E5 | 新版无任何承接线索 | **最可能是缺口**，但必须人工确认后才写 `GAP-`，不能凭 E5 自动判 |

E5 不等于「缺口」；E1 也不等于「已对齐」。等级只决定「要花多少时间核对」，判定词由人写。

## 4. 硬性约束（复核会查）

1. 376 行行行有判定词，无「未判定」，无空行。
2. 每个 `✅已对齐` 都带「Java 类 + 方法 + 测试名」三要素；测试名必须是仓库里真实存在的测试（能 `grep` 到）。
3. 每个 `缺口` 都能在主文件 §9.1 找到同编号 `GAP-` 条目；反之 §9.1 的 GAP- 也必须在表里出现。
4. 每个 `排除-` 都能指到 OP/D 编号，且该编号在决策记录里确实存在。
5. `旧版无功能` 必须附 PHP 文件与行号。
6. KPI-3a（缺口数 / App 端未迁移项）口径：**376 行里判为「缺口」的行数**，目标为 0；不为 0 时报告结论不得写 PASS。
7. 阶段 B（App 端）本批**不判定**，表中不得出现阶段 B 的行。

## 5. 扫描器自检（防假通过）

`python tests/compare/APPK-2/parity_scan.py --self-test` 必须 PASS，它验证四件事：

1. 往旧版源码里注入一个 `public function`，分母必须 +1（证明扫描器真的读源码，不是复述登记簿）；
2. 删掉一个 `public function`，分母必须 −1 且该文件进 `no_public_class`（证明对缺失敏感）；
3. 故意把期望分母改错，`build_report()` 必须阻断（证明分母核对不是摆设）；
4. 同一输入两次运行输出逐字节相同（可复现，供交叉复核）。

自检 FAIL → 扫描器不可用 → 报告不得开工。
