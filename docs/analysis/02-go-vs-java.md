## 02 Go 与 Java 选型对照（有条件推荐，待用户确认）

> 本文**不确定最终语言**，只说明两种选择的取舍，以及推荐成立需要满足的前提。
> 文中不引用没有测量依据的性能数字。凡是写到"资源占用更低"之类的地方，都是定性判断。真实数字需要在 PoC 阶段用同样的页面、同样的数据测出来。
> 关于现状的事实，引用的是 `01-current-state.md`。

### 1. 这个项目的特点决定了选型的关注点

依据 01 文档，下面几点比"语言快不快"更影响选型：

1. **核心是"内容 CRUD + 模板渲染 + SEO URL"**。前台主要是读多写少的列表页、详情页、播放页；后台有 39 个控制器，基本是表单增删改查。这类业务的瓶颈通常在数据库和缓存，不在语言本身。
2. **模板没法直接复用**。苹果CMS v10 的模板（包括不在备份里的线上模板）是 ThinkPHP 模板语法、`{maccms:*}` 标签，再加上模板里直接调用 PHP 函数。**Go 和 Java 都没有现成的引擎能运行这种模板**，所以两者在这一点上**成本相当**：要么改写模板，要么自己写一个兼容解析器。不要把"模板复用"当作区分两者的理由。
3. **采集是 IO 密集型**。现在是串行的，一页一个请求、同步翻页（01 第 7 节）。改成并发采集是重构能带来的明确收益。Go 的 goroutine 和 Java 21 的虚拟线程都能比较自然地实现，难点在限速、重试、断点续采和合并规则，不在并发原语。
4. **数据格式和协议是硬约束，与语言无关**。需要兼容的有：`$$$ / # / $` 播放串、`type_extend` JSON、`group_popedom` JSON、md5 密码、`user_check` cookie、苹果CMS 资源站的 JSON/XML 协议，以及 `mac_url` 的 URL 规则。
5. **第三方插件生态**。PHP 的 addons 插件两种语言都不能复用。仓库里只有一个未启用的插件（01 第 6 节），所以眼下的迁移负担很小。但这也意味着重构后**无法再使用苹果CMS 市场上现成的插件和模板**，属于长期成本。

### 2. 对照表

| 维度 | Go | Java | 针对本项目的取舍 |
|---|---|---|---|
| 后台 CRUD 开发成本 | 框架偏轻（Gin、Echo、GoFrame），表单校验、分页、权限等要自己组合或选脚手架（go-admin、GoFrame 自带的工具） | Spring Boot 生态完整，Spring Security、Validation、MyBatis-Plus 代码生成都很成熟，国内也有大量 RuoYi 一类的后台脚手架 | 后台功能多、业务规则多（会员、积分、订单、卡密、提现），**Java 的现成件更多**；Go 写起来代码更直白，但重复代码更多 |
| 沿用旧库（MyISAM，字段命名不统一，大量拼接 SQL） | sqlx 或 sqlc（手写 SQL，类型安全），也可以用 GORM | MyBatis / MyBatis-Plus 很适合手写 SQL 对接旧库，JPA 不太适合 | 两边都可行。建议**不使用重型 ORM 自动建表**，以 SQL 为主 |
| 采集并发 | goroutine 加 `errgroup` 或 worker pool，原生 `net/http` 就够用，部署成单独的 worker 进程很方便 | 虚拟线程（JDK 21）加 HttpClient，或者 WebClient；调度可以用 Spring Scheduler 或 Quartz | **Go 实现更轻、更自然**，Java 21 也能满足。两者的差距取决于团队熟悉哪一个 |
| 模板引擎（必须改写或适配旧模板） | `html/template`（安全但表达力弱）；pongo2（Django/Jinja 风格）；Jet；templ（编译型） | Thymeleaf、FreeMarker、Pebble（Twig 风格）、Beetl / JFinal Enjoy（国内常用，可以自定义标签） | Java 的模板引擎更多，自定义标签的机制也更成熟。如果要写一个"兼容 `{maccms:vod}` 标签的转换层"，**Java（FreeMarker/Beetl 的自定义指令）稍占便利**；Go 要多做一些自研 |
| 运维资源 | 编译成单个静态二进制，没有运行时依赖，内存占用和启动时间通常比 JVM 低（定性） | 需要 JVM，堆和 GC 要调参，基础内存占用比 Go 高（定性）；GraalVM native 可以缓解，但会增加构建复杂度 | 如果是**低配 VPS 或多站群部署，Go 更省心**；如果已有 JVM 运维体系，差别不大 |
| 生态与人才（国内） | 云原生和中间件方向的人多，CMS/后台类成熟开源项目相对少 | 企业后台、电商、支付的生态非常大，招人容易 | 取决于团队，**这一条需要用户回答** |
| 团队维护成本 | 语言小，代码风格统一，新人容易读懂 | 框架层次多（Spring 的约定、注解），上手和排错成本更高，但规范化程度也高 | 团队规模和现有技能**未知，需要用户回答** |
| 与现有静态资源的复用 | 静态 JS、CSS、播放器原样托管 | 同左 | 相同。`static/player`、layui、ueditor 都可以先保留 |
| 本机开发环境 | Go 1.26.4 已安装（`go version` 实测） | JDK 21 和 JDK 8 已安装。本机笔记里提到 Java 17 以上在这台 LTSC 机器上有 NIO loopback 问题；本次用最小的 `Selector.open()` 在 JDK 21 上测试**可以通过**，但没有用 Spring Boot 实测 | 只影响本地开发，不影响生产选型。Java 路线要先在本机跑通一个 Spring Boot 3 的 PoC |

### 3. 两种候选的框架方案和简化架构

**两种方案都建议采用"模块化单体 + 独立采集 worker"，暂时不做微服务。**

理由：
- 当前是单体 PHP，业务域之间共用一个库、强耦合（会员组权限依赖分类，播放依赖播放器配置）。
- 团队规模和流量都还不清楚。
- 拆微服务会额外带来分布式事务、服务发现、链路追踪的成本，而这些问题现在并不存在。
- 采集是唯一有明显不同运行特征的部分（长时间运行、IO 密集、需要限速），所以把它做成**同一个代码库里的另一个进程**即可，不需要拆成独立服务。

```
                ┌───────────── nginx（旧/新路由切换，灰度） ─────────────┐
                │                                                     │
          旧 PHP（逐步下线）                       新应用（模块化单体，一个仓库）
                                     ┌─────────────────────────────────────────┐
                                     │ web 进程：                               │
                                     │  site（前台渲染/SEO URL/播放页/sitemap）  │
                                     │  member（会员/会员组/积分/订单/卡密/提现）│
                                     │  admin（后台 API + 管理界面）             │
                                     │  openapi（Provide/Receive 兼容协议）      │
                                     │ worker 进程：collect / make / urlsend / 定时 │
                                     │ 共享：content 领域、配置中心、缓存、存储适配│
                                     └─────────────────────────────────────────┘
                                                │            │
                                          MySQL（先沿用旧库） Redis（缓存/锁/限流）
```

| | Go 方案 | Java 方案 |
|---|---|---|
| Web 框架 | Gin 或 Echo，加上自选组件；或者 GoFrame（全家桶，自带 ORM、配置、校验） | Spring Boot 3（JDK 21） |
| 数据访问 | sqlc 或 sqlx（手写 SQL），迁移用 golang-migrate 或 goose | MyBatis-Plus，迁移用 Flyway |
| 模板 | pongo2 或 Jet，加上自研的 `maccms` 标签函数集 | FreeMarker 或 Beetl 的自定义指令，实现 `maccms` 标签 |
| 后台界面 | 先保留 layui 页面并改造成调用新 API，或者新做 Vue 管理端（需要前端配合） | 同左，也可以套用 RuoYi-Vue 一类的脚手架 |
| 采集 worker | 同一个二进制用子命令启动（例如 `app worker collect`） | 同一个工程里的另一个 Spring profile 或启动类 |
| 定时任务 | robfig/cron，加上 Redis 分布式锁 | Spring Scheduler 或 Quartz，加上 Redis/ShedLock |
| 部署形态 | 单个二进制，加上 systemd 或 Docker | fat jar 或 Docker，需要 JVM |

### 4. 有条件推荐

- **在第 5 节的问题得到回答之前，本文不给出语言推荐。** 仓库里没有关于部署环境、团队、流量和业务范围的证据，不能据此偏向任何一方。按回答的情况，推荐这样分支：

  | 条件（来自第 5 节的回答） | 推荐 |
  |---|---|
  | 团队主力熟悉 Java/Spring，或已有 JVM 运维体系 | Java，其他条件基本不改变结论 |
  | 团队主力熟悉 Go，或团队愿意统一学 Go，接受重写模板或自研模板兼容层，且会员支付类业务没有大幅扩展的计划 | Go |
  | 团队两种都不熟，且主要维护者是现有 PHP 人员 | 先认真评估"继续使用 PHP 并加固"（见下一条），再决定是否重写 |
  | 团队两种都熟或都不熟，部署是资源受限的单机或多站点，采集量大是核心诉求 | 偏 Go（运维面更小，定性判断），需要 PoC 验证 |
  | 团队两种都熟或都不熟，会员、支付、财务、营销类业务要继续扩展，或计划招外包、扩大团队 | 偏 Java（后台和企业组件更成熟，招人面更广） |
  | 以上信号互相冲突（例如团队熟 Go，但会员支付业务要大幅扩展） | 用 03 第 7 节提到的 2～3 周 PoC，两种语言各做同一个只读详情页加采集 worker，比较开发效率和资源占用后再定 |

- **一个需要正视的备选：继续使用 PHP**。如果主要痛点是安全问题（01 第 10 节）和可维护性，在 PHP 端修复漏洞、补上依赖、迁移到 InnoDB，成本远低于整体重写。只有当目标是长期摆脱苹果CMS 架构、团队不想维护 PHP、或者要做大规模的定制化时，重写才划算。这一项**不作为本文的推荐**，只是列出来供用户决策。

### 5. 需要用户回答的问题（决定推荐是否成立）

1. **团队**：现在和未来半年，会有几个人维护这套代码？熟悉 Go、Java、PHP 中的哪些？后台前端由谁来做？
2. **动机**：重构最主要想解决的是什么？安全、性能、采集效率、二次开发困难、招人难，还是其他？
3. **流量和数据量**：日 PV 或峰值 QPS 大概多少？`mac_vod` 等主表有多少行？有没有站群或多域名？
4. **部署环境**：服务器配置（CPU、内存）、数量，是 VPS、云主机还是容器？有没有 CDN？预算有没有上限？
5. **模板**：线上用的是哪个模板？是购买的还是自己做的？能不能提供？允不允许改版？
6. **SEO**：线上实际的 URL 规则和伪静态开关是什么（需要脱敏后的 `maccms.php` 中 rewrite/view/path 部分，以及 `route.php`）？可以接受多少 301？
7. **功能范围**：会员、支付、卡密、提现、评论、留言、QQ/微信登录、站群、静态生成、自定义规则采集（Cj）中，哪些线上在用，哪些可以砍掉？
8. **插件**：线上有没有装过额外的插件，或者改过核心代码？
9. **时间**：期望多长时间完成第一阶段上线？能不能接受新旧系统并行几个月？
10. **安全问题**：01 第 10 节第 1～4 条（哈希登录、openid 登录、定时任务接口无鉴权、OAuth 建号用时间戳密码）是在本仓库代码中发现的，线上是否同样存在需要先核实。如果存在，是否同意先在 PHP 端修复？
