## 13 整体切换方案：停止旧站写入、新系统接管、对账、回滚门槛与整体切回（D3 / B07 ⑥ / MACC-31）

> **状态：方案文档，未执行。** 不部署、不切 nginx 流量、不停止任何真实 PHP 服务、不访问线上站点或数据库。依据：路线图（`09-roadmap.md`）D3 已决（第 9 节："上线时整体切换；不改旧 PHP、不做分阶段写入方切换；切换前的并行开发期新系统对生产只读"）、第 1.2 节（零结构变更、回滚只用 DML）、第 5.3 节 B07 ⑥ 与 B21、第 6 节回滚原则。写入基础设施与回滚工具见 `12-write-infrastructure.md`。
> 本方案在 B21 中于**本地开发库的一次性副本**上完整演练一次（停旧站写入 → 新系统接管 → 写入 → 对账 → 整体切回），演练记录补进本文第 9 节。真正的上线窗口需要用户另行批准（部署、切流量、生产账号都未获批准）。

### 1. 原则

1. **整体**：一次切换全部功能（前台、会员、后台、采集、接口、定时任务），不存在 PHP 与 Java 同时写库的阶段。
2. **不改旧 PHP**：停止旧站写入、切回旧站都只在 PHP 之外操作（nginx、php-cgi/php-fpm 进程、定时任务、文件快照），不改 PHP 代码，也不改旧站配置文件的内容。
3. **同一套表、同一种取值**：新旧系统读写同一套 26 张 `mac_*` 表，结构不变（零结构变更）。新系统写入的取值必须与旧版写入的一致（各写库批次的验收要点），这是"切回旧站时可以保留新系统期间数据"的前提。
4. **先停后切、先快照后写**：旧站停止写入且确认静止之后才取快照、才让新系统写库；回滚同样先停新系统写入再取快照。
5. **回滚只用 DML**：任何时候都不使用 `TRUNCATE`、`ALTER`、重建表、整库导入来回滚数据；整库逻辑备份只作为最后一道保险，由数据库管理员决定是否使用。

### 5. 对账

**a. 接管前（T+4，内网）**：对一组事先在旧站停止前录好的样本地址（首页、分类、详情、搜索、会员中心、后台主要页、Provide 接口），比较新系统的状态码与关键内容（标题、列表条目、分页数、金额与积分显示）。差异只能是各批次文档里列出的"有意差异"（含路线图第 5.5 节六项安全修复）。

**b. 观察期内（定时，例如每 15 分钟）**：

| 项 | 方法 | 通过标准 |
|---|---|---|
| 表结构 | information_schema 指纹与 S0 比对（B02 `SchemaFingerprint` 的同一套字段） | 完全一致 |
| 写入范围 | S0 → 当前的逐行 diff，按表统计；对照 `WriteRegistry` 登记表 | 只有登记过的表有变化 |
| 积分 | 每个有变化的用户：`user_points` 的变化 = 本期 `mac_plog`/`mac_ulog`/`mac_card`/`mac_order` 记录推算的变化 | 全部相等 |
| 订单与卡密 | `order_status`、`card_use_status`、`cash_status` 只出现旧版允许的状态转移；一张卡只被用一次；一个订单只到账一次 | 无异常转移 |
| 计数 | `*_hits`、顶踩、评分只增不减（后台手工修改除外） | 无减少 |
| 配置文件 | 与 S0 文件快照逐字节比较；有变化的文件必须是后台操作写回的，并能被旧 PHP 解析（`php -l` 与 B15 的黄金向量规则） | 无意外变化 |
| 人工对账项 | 日志中的"写入需人工对账"（12 文档第 4.4 节）条数 | 为 0，或已在窗口内逐条处理 |
| 错误率 | nginx 与新系统日志的 5xx 比例、登录失败率、支付回调失败数 | 不高于切换前同时段基线（基线在 T-1 天采集） |

### 6. 回滚门槛

**立即整体切回**（任一项）：

- 新系统无法启动或健康检查持续失败；
- 表结构指纹与 S0 不一致；
- 出现登记表以外的表被写入；
- 积分、订单、卡密、提现对账有任何不一致且不能在窗口内解释；
- 支付回调处理失败（到账未生效或重复到账）；
- 出现无法在窗口内处理的"写入需人工对账"项。

**评估后决定**（由用户或其授权人在窗口内拍板）：5xx 比例、登录失败率明显高于基线；页面差异超出各批次文档列出的有意差异；性能明显劣化。

**决定时限**：观察期内任何时候都可以切回；观察期结束、宣布切换完成之后再切回，按第 7 节同样的步骤，但新系统期间的数据量更大，第 7.3 节的处理工作量随之增加。

### 7. 整体切回旧 PHP

#### 7.1 停止新系统写入

1. nginx 切到维护配置，对全部入口返回 503；停用外部 cron 与采集推送。
2. 新系统平滑关闭（Ctrl+C / 按记录的 PID 停止，见 `backend/README.md`），等进行中的请求结束；确认静止（同第 4 节 T+2）。

#### 7.2 快照 S1 与差异

对 26 张表取 S1，与 S0 逐行比对，得到新系统期间的全部写入（新增、删除、变更，按表与主键列出，不打印列值）；文件同样与 S0 文件快照比较。

#### 7.3 数据处理（逐表决定，资金类表需用户确认）

- **默认保留**：新系统期间的会员注册、评论、订单、点击等是真实用户行为，取值与旧版相同（第 1 节原则 3），旧 PHP 可以直接读取。默认不恢复，只处理有问题的行。
- **需要撤销时**：用 `DmlRestore` 对选定的表或行生成并执行 DML（先删新增、再改回变更、再补回删除），执行后再取快照与目标比对，diff 必须为空。资金类表（`mac_user` 积分、`mac_order`、`mac_card`、`mac_cash`、`mac_plog`）只能在逐条核对后处理，并通知受影响的用户。
- **不允许**：`TRUNCATE`、`ALTER`、重建表、整库导入覆盖（会丢掉窗口外的数据，也违反零结构变更）。整库逻辑备份只在管理员判断数据已无法用 DML 修复时作为最后手段，由用户决定。
- **已知边界**：`AUTO_INCREMENT` 不回退（12 文档第 6 节），旧 PHP 之后插入的行 id 从新系统用过的最大值之后开始，不影响功能。

#### 7.4 文件与缓存

- 配置文件、模板、插件、上传目录：与 S0 文件快照不同且旧 PHP 不能使用的，按文件快照恢复（文件复制，不改 PHP 代码）。
- 清空旧站的运行缓存：`runtime/cache`、`runtime/temp`，以及 `maccms.php` 中 `app.cache_type` 指定的缓存存储（文件、Redis 或 Memcache，线上取值待 D9-b）——新系统期间数据变了，旧站缓存里的列表与详情已经过期。这是运维操作，不改代码与配置。

#### 7.5 恢复旧站

1. 启动 php-cgi/php-fpm；内网冒烟（同第 5 节 a 的样本）。
2. nginx 切回旧站配置；恢复指向 `api.php/timming` 的 cron 与采集推送；解除下单等入口的维护页。
3. 会话：新系统的会话在进程内存中，切回后会员与管理员需要重新登录（切换时同样如此，旧站的文件会话不迁移）。提前在公告中说明。
4. 记录：S0、S1、diff 统计、处理过的表与行数、处理后的 diff、各步骤时间。

### 8. 本方案不包含

- 任何 PHP 代码改动、旧站配置内容改动、数据库账号或权限的程序化调整（账号由管理员按第 2 节准备）。
- 分阶段（按表或按功能）切换写入方——D3 已决撤回。
- 部署、切流量、线上核实——均未获批准。
