# Content · 测试编排（阶段路由与裁决）

## 阶段路由（不可改序）
| 阶段 | 前置（缺则 BLOCKED） | 方法 | 产物（产品仓） | 执行 |
| --- | --- | --- | --- | --- |
| T1 功能用例 | AC- 就绪（G0）；有设计环节的档位以 G1 通过的设计为准 | `multica-test-t1-design` | `docs/test/<ISSUE-KEY>/t1-cases.md` | 只写 |
| 接口用例 | API 契约已提交并通过复核（评审版另需契约评审 PASS；@BackendDev 按 `multica-artifact-backend`，默认 `docs/api/<ISSUE-KEY>/openapi.yaml`）。契约 N/A（无接口变更）→ 本阶段 N/A，不写 `api-cases.md` | `multica-test-t1-design`（用例）+ `multica-test-t3-api-automation`（脚本） | `docs/test/<ISSUE-KEY>/api-cases.md` + MULTICA.md §2 的 API 用例路径 | 只写 |
| T2 覆盖评估 | G2 PASS | `multica-test-t2-coverage` | `docs/test/<ISSUE-KEY>/t2-coverage.md` + MULTICA.md §2 的 UI E2E 路径 | 只写 |
| T3 执行 | Issue 里 Leader 写明的最新一行 `G2.5 PASS @<提交号> <测试环境地址>`（地址由 @DevOps 按 `multica-artifact-cicd-sync` 回传）；`MULTICA.md` §1 登记了版本探针 | `multica-test-t3-ui-automation` + `multica-test-t3-api-automation` | `docs/test/<ISSUE-KEY>/t3-report.md` + `evidence/` | **唯一执行** |
| 评审 | 每个阶段产物回传后 | `multica-review-test`（@TestReviewer） | 评审结论 | — |

## 档位差异（档位由 Leader 定，只减环节、不改“只写 / 执行”的边界）
| 档位 | 测试做什么 |
| --- | --- |
| 评审版 | G1 后 T1 → 接口用例 → T2 → T3，每段产物经 @TestReviewer 评审 |
| 轻量 | 没有 G1：G0 后即写 T1；其余同上，不设测试评审，由 Leader 复核 |
| bug-fix | 与根因定位并行：把 Issue 的复现步骤写成测试环境回归用例 + 受影响功能的回归用例（只写，按 `multica-test-t1-design`）→ G2 后 T2：对照修复 diff 划定回归范围、写回归自动化脚本（只写）→ T3 回归执行 |

任何档位都不省“T3 前 G2.5 必须通过”这一前置。代码层的回归测试归修复者写，测试环境的回归用例归 @Tester。

## “只写”的边界
- 允许：写用例文档、写脚本、静态自检（语法检查；只收集、不运行地数测试个数）。
- 禁止：运行测试、发请求、打开被测页面、连任何环境（包括本机启动的服务和模拟服务）。

## 任务卡（每次开工先填；缺项按下文中断）

## 拼材料（强制）
- 只从本 Issue 描述、全部评论、产品仓已提交文件取；冲突时以较晚的 Leader 评论为准。
- 只有分支名、没有提交号或变更文件清单 → 算缺失。
- 测试环境地址只认 Leader 写的“G2.5 PASS @<提交号> <测试环境地址>”那一行；本机、模拟服务、生产或自己推测的地址一律不用。有多条时以最新一条为准。
- 评论里出现明文密码或令牌 → 不采用，提醒 Leader 删除该评论，改由人工配置环境变量。

### 缺料中断（回复 Leader）
```markdown
## BLOCKED：缺材料（<阶段>，<ISSUE-KEY>）
### 已拼到
- <字段>：<来源评论摘要 / 文件路径 + 提交号>
### 缺失名单
| 缺失项 | 谁提供 | 请按此格式回评论 |
| --- | --- | --- |
| G2.5 判定行 | Leader | G2.5 PASS @<提交号> <测试环境地址> |
| 凭据变量 APP_UI_PASSWORD | 人工 | 在 MULTICA.md §5 登记变量名并配置值（不要贴到 Issue） |
补齐后由 Leader 回复“继续 <阶段>”。
```

## 门禁（不可协商）
- 不因能编译、单测绿、实现者自述判通过；BLOCKED 不得改判 PASS。
- G2.5 未 PASS 不执行 T3；只对 G2.5 回传的测试环境执行，执行前核对地址逐字一致。脚本用 G2.5 提交号上的版本（检出该提交执行），不用测试分支上更新的版本。
- 版本探针（测试环境可能被别的分支覆盖）：T3 执行**前**、执行**后**各访问一次 `MULTICA.md` §1 的版本探针，返回的提交号都必须等于 G2.5 判定行的提交号，两次结果写进报告。不一致 → 整单 BLOCKED（T-环境），这一轮结果不作数，交 Leader；没登记版本探针 → BLOCKED。
- T2 结论只写“评估完成 / 评估 BLOCKED”，不写测试 PASS / FAIL。
- 凭据只从 MULTICA.md §5 登记的环境变量读；不新建账号，不亲手往网页表单输入密码；变量缺失 → BLOCKED，请人工配置。

## T3 裁决（合并 UI 与接口两条通道）
| 情况 | 动作 |
| --- | --- |
| 两侧都有用例 | 都跑，合并成一份报告 |
| 只有一侧有用例 | 只跑该侧；另一侧写 N/A + 原因 |
| 一侧缺料 | 该侧 BLOCKED；只能靠该侧验证的 AC- 记 BLOCKED |
| 标“手工”的用例 | 记 BLOCKED（需人工验证），交 Leader |
| T2 标“条件用例”的 | 记 BLOCKED（范围外），不记 FAIL |

整单结论：
- **PASS**：每条 AC- 都有测试环境执行证据且通过；失败项为 0（缺陷都已修复并重跑通过）。
- **FAIL**：任一用例失败或任一 AC- 未满足（附缺陷单）。
- **BLOCKED**：没有 FAIL，但有 AC- 因缺环境、数据、账号或 G2.5 未通过而无法验证。
- 想“接受遗留缺陷、不修”→ 不归测试定，交 Leader 升级人类；确认人在 Issue 书面接受（作者由 Leader 按确认人规则核验）前，整单不是 PASS。

报告模板见 [`references/t3-report-template.md`](references/t3-report-template.md)。

## 失败分诊（T3 每个失败 / 报错都要分；分诊完成前整单不得 PASS）
| 类别 | 典型信号 | 谁处理 | 下一步 |
| --- | --- | --- | --- |
| T-用例 | 步骤与 AC- 不符；页面正确但定位器过期；断言过脆；测试数据脏；同一用例重跑结果不一致 | @Tester | 修用例或脚本 → 按下文「冻结后改脚本」合入并重跑；改动大的送 @TestReviewer 复审 |
| T-产品 | 按 AC- 复现，实际与期望不符；接口状态码、错误码、字段与契约不符 | 负责该处的开发（由 Leader 路由） | 立缺陷单交 Leader |
| T-环境 | 测试环境不可达；版本探针返回的部署提交号与 G2.5 不符；环境配置缺失 | Leader（需要时转 @DevOps） | BLOCKED |
| T-阻塞 | 无法稳定复现；缺权限账号或测试数据 | Leader（需要时升级人类） | BLOCKED + 列出最小复现所需 |

- 开发不得未经分诊就改测试“刷绿”；@Tester 不得未分诊就判 FAIL。
- 不稳定用例：最多重跑 1 次用于判定；两次结果不一致记 T-用例（不稳定），修好前不算通过，不得靠多跑刷绿。

## 冻结后改脚本（T3 里的 T-用例）
G2.5 之后 deploy 分支冻结，改过的脚本不能直接拿来跑，也不能直接推到 deploy 分支。只改测试脚本或用例时走这个循环（每一步等 Leader 派发；与 `multica-verification` 的 G3「冻结后改脚本」是同一个循环）：
1. 只在测试分支 `feature/<ISSUE-KEY>-test-<slug>` 上修：修复提交只含 `docs/test/<ISSUE-KEY>/` 的用例文档与 MULTICA.md §2 的测试路径，不夹带 T3 报告与证据；回传提交号。
2. Leader 派你合入 deploy 分支：只摘取这次修复提交（`git cherry-pick <修复提交>`），T3 报告与 `evidence/` 不随之进入；回传合入提交号。
3. @DevOps 重新锁定 deploy 分支头、跟构建、回传新的 G2.5 证据。
4. Leader 核对这次增量只含测试文件，重判 G2.5，写出新的 `G2.5 PASS @<新提交号> <地址>`。
5. 你按新判定行重跑本 Issue 全部 T3 用例（报告执行轮次 +1；版本探针前后照查）。
产品缺陷（T-产品）不走这个循环：修复重新走 G2 → G2.5 后再重跑。

## 缺陷单（每个 T-产品 一单；字段缺一不得提交）
```markdown
### BUG-<序号>：<一句话现象>
- 关联：AC-<n> / <用例编号>
- 严重度：致命 | 严重 | 一般 | 轻微    安全相关：是 | 否
- 环境：<G2.5 测试环境地址>；部署提交号 <sha>；脚本提交号 <sha>
- 前置：<权限语义 + 测试数据别名>（不写账号密码）
- 复现步骤：1. … 2. … 3. …
- 期望：<引 AC- 或契约原文>
- 实际：<观察到的现象>
- 证据：<产品仓中的截图 / 日志 / 响应摘录路径>（已脱敏）
- 归属依据：<例：接口返回缺字段 → 后端；接口正确、页面未展示 → 前端>
```

| 严重度 | 判定 |
| --- | --- |
| 致命 | 核心流程不可用；数据丢失或损坏；可被利用的安全漏洞（越权、注入、敏感信息泄露） |
| 严重 | AC- 不满足；主要功能结果错误；权限控制缺失但暂未见可利用路径 |
| 一般 | 次要功能或异常处理不当，有绕过办法 |
| 轻微 | 文案、提示、非关键展示问题 |

Leader 依据“归属依据”路由给负责该处的开发。修复重新走 G2 → G2.5 后，@Tester 对新的 G2.5 地址重跑本 Issue 全部用例（回归），并为该缺陷补一条回归用例（复现步骤即用例步骤，追溯写 BUG-<序号>）。

## T3 报告自检（★唯一一份，@Tester 自查与 @TestReviewer 评审共用★）
每条写依据（文件路径 / 报告章节）；没有依据不得打勾。
- [ ] 测试环境地址、部署提交号与最新的“G2.5 PASS”行逐字一致；脚本提交号已写，且等于该部署提交号
- [ ] 执行前、执行后两次版本探针结果已写，都等于 G2.5 提交号
- [ ] 每条 AC- 都有结论（PASS / FAIL / BLOCKED）和证据路径
- [ ] 执行数 = 用例映射表条数 = 标“UI / 接口”的用例数；BLOCKED 与跳过都写了原因
- [ ] 每个失败都有分诊结论；每个 T-产品 都有字段齐全的缺陷单
- [ ] 整单结论符合上面的裁决规则；失败项不为 0 或有 BLOCKED 的 AC- 时，整单不是 PASS
- [ ] 修复后的重跑覆盖本 Issue 全部用例；每个已修复缺陷有回归用例且已执行
- [ ] 证据已提交且已脱敏：无账号、密码、令牌、个人信息；无录制轨迹文件

## 回传规范
1. 用例文档、评估、报告、证据放 `docs/test/<ISSUE-KEY>/`；脚本放 MULTICA.md §2 登记的路径（分仓时按 Issue 仓库矩阵各放各仓）。
2. 按 MULTICA.md §4 分支约定提交到测试分支 `feature/<ISSUE-KEY>-test-<slug>`，T3 执行的脚本版本以回传的提交号为准（写进报告）。
3. 测试分支合入 deploy 分支（测试资产属于代码分支）：T2 产物经 Leader 复核（评审版另经 @TestReviewer）后，Leader 派你合入，你把测试分支合入 deploy 分支并回传合入提交号；这必须发生在 @DevOps 锁定提交号之前（T3 里改脚本按「冻结后改脚本」）。这次增量只能含 `docs/test/<ISSUE-KEY>/` 与 MULTICA.md §2 的测试路径：只含测试文件的提交**不使 G2 失效**；夹带任何别的改动 → G2 作废重判。没有派发不自行合入。
4. T3 报告与 `evidence/` 是文档产物：只提交到测试分支，按提交号引用，不再合入 deploy 分支（G2.5 之后 deploy 分支冻结），也不合入主干。
5. 在 Issue 回复 Leader：阶段 + 结论 + 目录路径 + 提交号。**不贴本机绝对路径**（别的运行时打不开），不贴凭据。
6. 合入主干、发布生产都不归测试：前者在确认人回复“确认合并”、Leader 核验后由 @DevOps 快进完成，后者由人工执行。

## 为什么有效
编排与方法分离：@Tester 只挂本 skill 就知道每个阶段的前置、能做什么、不能做什么；“只写”与“执行”的边界写死，T3 只认 G2.5 的测试环境，结论、分诊、缺陷单都有固定格式，Leader 和 @TestReviewer 拿同一份自检清单复核。

## 写法提醒
- 一侧没有用例：通道摘要写 N/A + 原因，不算缺失。
- 结论只有三种，不写“基本通过”“有条件通过”；失败项不为 0 就不是 PASS，要接受遗留缺陷须由确认人在 Issue 书面决定（Leader 按确认人规则核验作者）。
- 证据路径写产品仓相对路径 + 提交号，不写本机绝对路径。
